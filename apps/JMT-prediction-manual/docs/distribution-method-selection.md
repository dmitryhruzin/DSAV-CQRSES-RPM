# Выбор закона распределения service-time для JMT-модели

Документ описывает рассуждение, как мы пришли к текущему выбору распределения для service-time в JMT-модели. Структура: терминология → данные → способы калибровки → варианты выбора семейства → план экспериментов.

## 1. Что такое service-time distribution в JMT

В JMT каждая станция обслуживает поступающие job-ы. На каждый job симулятор берёт случайное число из заданного распределения — это и есть «сколько мс уйдёт на обслуживание этого job в этой станции». Параметры (mean, variance/CV², shape) определяют форму. На каждой паре (station, class) можно задать **своё** распределение независимо от других.

## 2. Базовая терминология

### CV² — квадрат коэффициента вариации

```text
CV² = σ² / μ²
```

Инвариант к масштабу. Показывает, насколько разлёт значений «больше или меньше», чем у экспоненциального распределения. Для Exp ровно CV²=1 по построению.

- `CV² < 1` → распределение **менее разбросано** (концентрация вокруг среднего): Erlang/Gamma/Lognormal с маленькой σ.
- `CV² = 1` → собственно Exp.
- `CV² > 1` → тяжёлый хвост: HyperExp, Pareto, Lognormal с большой σ, Weibull (k<1).

### CDF — функция распределения

`F(x) = P(X ≤ x)` — «какая доля значений в выборке ≤ x». Например, в нашем PATCH `db.eventstore.write` на m7i-io2 seq:

```text
F(0.20) = 0.40   → 40% запросов уложились в ≤ 0.20 мс
F(0.23) = 0.50   → медиана
F(0.35) = 0.95   → p95
F(1.00) = 0.99
F(25.0) = 1.00
```

У каждого теоретического распределения тоже есть своя CDF. У Lognormal:

```text
F_LN(x) = Φ((ln x − μ) / σ)
```

где Φ — CDF стандартной нормали. Хороший фит = эти две CDF совпадают по всей оси x.

### MOM — метод моментов

Подгоняем (μ, σ) распределения так, чтобы у него **совпали среднее и дисперсия** с эмпирическими. Для Lognormal — закрытая форма:

```text
σ² = ln(1 + variance / mean²) = ln(1 + CV²)
μ  = ln(mean) − σ² / 2
```

### MLE — метод максимального правдоподобия

Подгоняем (μ, σ) так, чтобы **вероятность увидеть нашу выборку** под выбранной моделью была максимальной. Для Lognormal это эквивалентно: возьми `ln(xᵢ)` от каждого сэмпла и подгони к ним обычную нормаль:

```text
μ_MLE  = mean(ln(xᵢ))
σ²_MLE = mean((ln(xᵢ) − μ_MLE)²)
```

Логарифм сжимает большие значения, поэтому MLE робастен к редким выбросам, в отличие от MOM, где `(x_max − μ)²` напрямую раздувает variance.

### KS — Kolmogorov-Smirnov distance

```text
KS = max_x | F_empirical(x) − F_model(x) |
```

Самое большое вертикальное расхождение между двумя CDF. Шкала:

- KS < 0.05 — отличный фит
- 0.05–0.10 — приемлемый
- 0.10–0.20 — посредственный
- > 0.20 — плохой

## 4. MOM vs MLE: эксперимент

Проверили на 72 (file × method × metric)-комбинациях, какая стратегия фита Lognormal даёт меньший KS — [_fit_compare.mjs](../_fit_compare.mjs) → [log-fit-comparison.md](../log-fit-comparison.md).

**Итог: MLE выигрывает в 67 из 72 (93%)**, особенно драматично на heavy-tail DB-метриках:

| Станция (пример m7i-io2 seq) | KS_MOM | KS_MLE | Δ |
| --- | --- | --- | --- |
| POST `db.eventstore.write` | 0.564 | **0.188** | −0.376 |
| PATCH `db.eventstore.write` (CV²=7.49) | 0.663 | **0.217** | −0.446 |
| PATCH `db.projection.write` | 0.590 | **0.224** | −0.366 |
| PATCH `db.projection.read` | 0.394 | **0.240** | −0.154 |
| GET `db.projection.read` | 0.350 | **0.157** | −0.193 |
| AppService (POST `cmd+pub−DB`) | 0.199 | **0.158** | −0.040 |

На примере PATCH `db.eventstore.write`:

```text
MOM:   μ=−2.328,  σ=1.463  → LN-медиана = exp(μ) = 0.097 мс
MLE:   μ=−1.398,  σ=0.339  → LN-медиана = 0.247 мс
эмпирика:                  → медиана    = 0.232 мс
```

MOM-фит ушёл от истинной медианы в 2.4 раза из-за 3 выбросов (24, 18, 13 мс) в выборке из 2158. MLE их «сжал» через ln и оценил bulk правильно.

5 случаев, где MOM выиграл — все при очень низком CV² (0.08–0.30), Δ KS = +0.01…+0.05, в пределах шума.

**Решение:** для всех станций используем **MLE** вместо MOM.

## 5. Замечание: даже MLE Lognormal не идеален

После перехода на MLE KS-метрики по большинству станций лежат в **0.15–0.35**. Это «посредственный» уровень. Причина — реальные service-time распределения у нас часто **бимодальные**: быстрый cache-hit + редкий cache-miss + ещё реже WAL-flush. Lognormal одногорбое, одной σ не хватает.

Поэтому возникает вопрос: остаться на одном Lognormal MLE или выбирать распределение **per-station** под форму данных?

## 6. Варианты выбора семейства

### Вариант A: универсальный Lognormal MLE

Одно семейство, разные (μ, σ) на каждой станции.

**Плюсы:**

- Просто и единообразно.
- K-масштабирование при предсказании работает чисто: `μ' = μ + ln(K), σ — без изменений`.
- Уже валидирован в [JMT-prediction-v4](../../JMT-prediction-v4/report_v4.md): MRE avg 11.1%, лучше чем Exp/HE.

**Минусы:**

- KS 0.15–0.35 на большинстве станций — не блестящий фит.
- Бимодальность не ловится.

### Вариант B: эвристика Brunnert et al. (2015)

В работе **Brunnert et al., *Performance-oriented DevOps: A research agenda*, SPEC RG 2015** для построения PRO-моделей предлагается выбирать семейство **по CV²**:

```text
CV² < 0.5       →  Erlang-k,  k = round(1 / CV²)
0.5 ≤ CV² ≤ 1.5 →  Exponential
CV² > 1.5       →  HyperExp (или Lognormal)
```

Логика: под каждый диапазон выбирается семейство, которое **естественно живёт** в этом диапазоне:

- Erlang-k имеет ровно CV² = 1/k — узкое распределение для CV²<1.
- Exp имеет CV² = 1 — для среднего диапазона.
- HyperExp/Lognormal с большой σ — для тяжёлых хвостов.

#### Как это легло бы на наши станции (по m7i-gp3 seq)

| Станция (класс) | CV² | Brunnert → | Параметры |
| --- | --- | --- | --- |
| AppService GET | 0.28 | Erlang-4 | k=4, rate=4/mean |
| AppService POST | 0.11 | Erlang-9 | k=9 |
| AppService PATCH | 0.17 | Erlang-6 | k=6 |
| RC AppService POST | 0.38 | Erlang-3 | k=3 |
| RC AppService PATCH | 0.23 | Erlang-4 | k=4 |
| GET ProjectionDB read | 1.89 | HyperExp/LN | LN с large σ |
| EventStore POST | 3.13 | HyperExp/LN | LN |
| EventStore PATCH | 3.57 | HyperExp/LN | LN |
| SnapshotDB POST | 1.88 | HyperExp/LN | LN |
| SnapshotDB PATCH | 0.76 | Exp | rate=1/mean |
| RC ProjectionDB.w POST | 0.29 | Erlang-3 | k=3 |
| RC ProjectionDB.w PATCH | 3.97 | HyperExp/LN | LN |
| RC ProjectionDB.r PATCH | 2.68 | HyperExp/LN | LN |

**Плюсы:**

- Каждое семейство «родное» для своей зоны CV² → KS-фит на каждой станции должен быть лучше, чем универсальный LN.
- Erlang отлично дружит с queueing theory — есть аналитические формулы для M/E_k/1 (sanity-check без JMT).
- Опубликованная, цитируемая эвристика в performance engineering.

**Минусы:**

1. **Между машинами CV² может попасть в разные бакеты** для одной и той же станции:
   POST `db.snapshot.r+w` имеет CV² = 0.48 на m7i-io2, **1.88** на m7i-gp3. По Brunnert это Exp на одном, LN на другом. Если калибруем m7a-io2 предсказанием из m7a-gp3 — пришлось бы менять семейство при K-масштабировании, теряя смысл единой модели.
2. **K-масштабирование Erlang работает чуть менее чисто**, чем Lognormal. Erlang(k, rate): mean = k/rate, CV² = 1/k. При scaling mean на K: rate' = rate/K, k фиксирована. OK, но `k` нельзя двигать.
3. **Эвристика принимает решение по голому CV² без учёта формы.** В нашем случае CV²=7.5 на eventstore.write — это **3 выброса из 2158**, а не настоящий heavy tail. Brunnert просто переключит на LN/HyperExp, не зная контекста.

### Вариант C: гибрид по качеству фита

1. Lognormal MLE как глобальный baseline.
2. Считаем KS на каждой станции.
3. Решение о переключении — **по KS**, не по CV²:
   - KS < 0.15 → оставляем LN MLE.
   - KS 0.15–0.25 → пробуем Erlang-k (если CV²<0.5) или HyperExp (если CV²>1.5); оставляем лучший по KS.
   - KS > 0.25 → Replayer (для калибровочных машин) или mixture-of-LN.

**Плюсы:**

- Решение основано на **измеренном качестве фита**, а не на эвристическом CV²-пороге.
- Lognormal сохраняется там, где он хорош.
- Робастнее к outlier-эффектам, искажающим CV².

**Минусы:**

- Более сложная имплементация (нужно фитить несколько семейств и сравнивать).
- Бо́льшая трудоёмкость аналитики на каждой станции.

## 7. Per-station и per-machine флексибельность

JMT в .jsimg позволяет указывать **отдельную ServiceStrategy для каждой пары (station, class)**, причём на **каждой машине** (= jsimg-файле) независимо. В нашем существующем v4-коде это видно ([build_jsimg.py:220-237](../../JMT-prediction-v4/build_jsimg.py#L220-L237)): функция `serv_block_for_station` собирает per-station блок, и текущая реализация просто использует один режим (`--mode exp|hyperexp|lognormal`) для всей модели, но ничего не мешает варьировать.

### Особенность нашего сетапа

У нас **измерены все 4 машины** (m7i-gp3, m7i-io2, m7a-gp3, m7a-io2), а не только база + K-масштабирование. Это значит:

- Можно калибровать каждую машину **независимо**, не привязываясь к K-формуле.
- Распределение на (machine, station) может отличаться от распределения на (другая_machine, та же station) — это не запрещено и даёт больше точности на конкретной машине.
- Для **предсказанного** M7a.io2 (если бы мы его прятали и предсказывали) нужно держать согласованное семейство, потому что K требует одной формы. Но в текущем экспериментальном сетапе всё измерено — это не ограничение.

Значит, в калибровочной фазе допустимы оба подхода:

1. **«Жёсткий»**: единое решение про семейство применяется ко всем 4 машинам (например, Lognormal MLE везде → проще, более универсально).
2. **«Гибкий»**: на каждой (machine, station, class) подбираем своё семейство по KS.

«Гибкий» даст лучший KS на каждой машине, но усложняет последующее сравнение моделей между машинами (если потом захочется построить K-карту вторично).

### 7.1 Можно ли менять семейство для одной станции между машинами?

Технически — да, JMT каждой машине задаёт свой `.jsimg`. Но **K-prediction теряет смысл**, если семейство разное на m7i и m7a.

Конкретный пример — **EventStore**:

| Машина | Class | CV² | σ_LN (≈) |
| --- | --- | ---: | ---: |
| m7i-gp3 | POST | 3.13 | 1.18 |
| m7i-io2 | POST | 3.17 | 1.20 |
| m7a-gp3 | POST | 0.82 | 0.79 |
| m7a-io2 | POST | 0.52 | 0.65 |
| m7i-gp3 | PATCH | 3.57 | 1.23 |
| m7i-io2 | PATCH | 7.49 | 1.46 |
| m7a-gp3 | PATCH | 0.72 | 0.75 |
| m7a-io2 | PATCH | 2.12 | 1.06 |

На m7i — heavy tail (CV² ≈ 3). На m7a — почти Exp (CV² ≈ 0.7–0.8). Brunnert-эвристика разнесёт m7i в Lognormal и m7a в Exp.

**Что в этом плохо для K-prediction:** наша формула предсказания

```text
K_disk  = D(m7i-io2) / D(m7i-gp3)
D(m7a-io2_predicted) = D(m7a-gp3) × K_disk
σ_predicted = σ(m7a-gp3)
```

работает на уровне (mean, σ). Когда мы переносим «закон, как диск меняет performance» с m7i на m7a, мы предполагаем, что **форма распределения** остаётся та же — меняется только масштаб. Если на m7i мы говорим «HE-форма», а на m7a — «Exp-форма», то формула не определена: σ-параметра у Exp нет, у HE есть, перенести нечего.

**Физическая интуиция:** σ_LN — свойство **инстанса** (CPU+memory+software stack), а не диска. Внутри m7i (gp3↔io2) σ одинаковая (1.18 ↔ 1.20 для POST), внутри m7a — тоже (0.79 ↔ 0.65). А между m7i и m7a — разная: AMD ZEN5 на m7a даёт более стабильный pipeline, чем Sapphire Rapids на m7i. Это **должно отражаться разными σ на разных инстансах**, но **одинаковым семейством** — иначе мы теряем способность перенести «закон диска».

**Lognormal MLE** прекрасно с этим справляется: даёт LN(σ≈1.2) на m7i и LN(σ≈0.79) на m7a, и K-prediction остаётся консистентной. **Brunnert же ломает** консистентность — для EventStore выбирает разные семейства per-instance-family.

**Вывод:** даже если технически можно — для нашего экспериментального сетапа с K-prediction единое семейство по машинам важнее, чем «лучший местный фит». Это аргумент в пользу LN MLE как универсального выбора.

### 7.2 Ограничения метода K-prediction

Чтобы коэффициент K вообще можно было применить к параметрам распределения станции, метод опирается на **два обязательных ограничения**. Они не дефекты, а условия корректности: при их нарушении формула масштабирования математически не определена.

**Ограничение 1 — единое семейство распределения на всех машинах.**
K-prediction сдвигает только параметр положения, не трогая параметр формы:

```text
μ_predicted = μ(m7a-gp3) + ln(K)
σ_predicted = σ(m7a-gp3)        ← наследуется без изменений
```

Перенести параметры можно, только если на исходной (m7i, m7a-gp3) и предсказываемой (m7a-io2) конфигурациях распределение принадлежит **одному семейству**: тогда у обеих сторон есть пара (μ, σ), и сдвиг определён. Если семейство меняется между машинами (как у Brunnert: Lognormal на m7i, Exponential на m7a для EventStore — см. §7.1), то переносить нечего — у Exp нет σ, у LN есть. Поэтому метод совместим только с **универсальным семейством** (Lognormal MLE).

**Ограничение 2 — инвариантность «закона диска» K между инстансами.**
Коэффициент измеряется на референсной паре m7i, а применяется к m7a:

```text
K = center(m7i-io2) / center(m7i-gp3)        ← измерено на m7i
center(m7a-io2) = center(m7a-gp3) × K        ← применено к m7a
```

Это корректно лишь при допущении, что отношение io2/gp3 — свойство **диска**, инвариантное к инстансу, и поэтому одинаково на m7i и m7a. Физическое обоснование (§7.1): σ — свойство инстанса (CPU+memory+stack), а множитель центра от смены диска — свойство диска. Если архитектура CPU взаимодействует с подсистемой ввода-вывода нелинейно (Sapphire Rapids на m7i vs AMD Zen5 на m7a), перенос K вносит систематическую ошибку, которую в пределах held-out проверить полностью нельзя.

**Итог:** оба ограничения сводятся к одному требованию — **форма распределения постоянна, меняется только масштаб центра**. Lognormal MLE его удовлетворяет; именно поэтому он выбран как универсальное семейство, а не эвристика per-CV².

## 8. Replayer как нулевая параметрическая опция

JMT поддерживает **Replayer** (`jmt.engine.random.Replayer`) — оно не параметрическое, а сэмплирует значения из CSV-файла. Можно скормить ему наши raw-сэмплы (`event.handle − projection.read − projection.write` для PATCH в виде списка значений), и симулятор будет на каждом job брать одно из реальных измерений.

**Плюсы:**

- Идеально воспроизводит выборку (KS=0).
- Не нужен fitting → нет шума от выбора семейства.

**Минусы:**

- Если sample size меньше количества job в симуляции, JMT начнёт повторять значения → корреляции артефактами.
- Сложнее экстраполировать на другой target load: distribution жёстко завязан на исходные условия.
- Для **predicted** машины через K-формулу не работает (CSV не масштабируется).

## 9. План экспериментов

Чтобы не делать выбор «на глаз», прогоним **два эксперимента** и сравним предсказание JMT-модели с измеренными load-данными:

### Эксперимент 1: Lognormal MLE на всех станциях

- Калибровка из seq-логов через MLE.
- Один и тот же режим распределения (Lognormal) везде.
- JMT-симуляция при arrival rates load-сценария.
- Сравнение предсказанных response time с измеренными по avg/median/p90/p95.

### Эксперимент 2: Brunnert-эвристика (per-station по CV²)

- Калибровка из seq-логов:
  - CV² < 0.5 → Erlang-k, MLE-fit
  - 0.5 ≤ CV² ≤ 1.5 → Exp с rate=1/mean
  - CV² > 1.5 → Lognormal MLE (берём Brunnert-вариант с LN, не HyperExp, потому что HE требует CV²>1 и плохо для CV²~1.6-2)
- JMT-симуляция и сравнение с измерениями.

### Что меряем

Для каждого эксперимента:

1. **KS-фит per station** (как метрика качества калибровки).
2. **MRE-предсказания** относительно measured load:
   - per-class (Zapyty / Stvor / Onovl / RC)
   - per-machine (m7i-gp3 / m7i-io2 / m7a-gp3 / m7a-io2)
   - на статистиках avg, median, p90, p95

### Решающий критерий

Выбираем подход, у которого **aggregate MRE по avg/median** меньше. Если разница на грани шума (< 2 п.п.), выбираем **более простой** (Lognormal MLE).

При значительной победе Brunnert (>5 п.п.) — фиксируем гибкий подход в pipeline.

## 10. Литература

- **Bertoli, Casale, Serazzi (2009)** — *JMT: Performance Engineering Tools for System Modeling* — каталог распределений JMT, важность подгонки по двум моментам.
- **Casale, Serazzi (2013)** — *Quantitative System Performance with Java Modelling Tools* — рекомендации подбирать распределение под форму эмпирической CDF per-station.
- **Brunnert et al. (2015)** — *Performance-oriented DevOps: A research agenda*, SPEC RG report — эвристика выбора семейства по CV² (вариант B).
- **Crovella, Bestavros (1997)** — *Self-Similarity in World Wide Web Traffic*, IEEE/ACM ToN — обоснование heavy-tail для веб-сервисов.
- **Mor Harchol-Balter (2013)** — *Performance Modeling and Design of Computer Systems: Queueing Theory in Action*, Cambridge UP, гл. 20 — рекомендует Lognormal как дефолтный выбор для service times.
- **Crovella, Taqqu, Bestavros (1998)** — *Heavy-tailed Probability Distributions in the WWW*.
- **Наш собственный [JMT-prediction-v4](../../JMT-prediction-v4/report_v4.md)** — LN даёт лучшие avg/median MRE среди трёх распределений (11.1% avg против 14.4% у Exp).
